## 2026-10-18 · 《Deepseek V4.1Flash1017 四个项目测试》—— 40 分钟里 28 分钟卡在一个下载

**视频**：BV1hrJz6jEJ5，14:10，169 MB / 1080p，A 型（技术工具横评）
**交付**：HTML + PDF，26 页；评论样本 95/292，8 个观点簇
**触发复盘的原因**：用户反馈"比其他时候慢得多"。同期同类型（10-17 那期 7:41）只用了 18 分钟。

### 时间去哪了

| 阶段 | 实测 | 基线 | 白费 | 病因 |
|---|---|---|---|---|
| 取数（元数据/字幕/评论） | ~30 s | 10–20 s | — | 一次成功，正常 |
| **视频下载** | **28 min** | 3–5 s（该基线只对 ≤50 MB 成立） | **~27 min** | 见下面的时间线 |
| 抽帧 + 读图 | 2.5 min | 15–20 s | ~1.5 min | 8 张图（3 联系表 + 5 原图），其中 1 张裁剪放大必要 |
| 写作 | ~10 min | — | 0 | 必要 |
| 渲染 + PDF 自检 | 4 min | 1 min | ~2.5 min | 定性卡改了 4 版，4 次渲染 |
| **合计** | **~40 min** | ~12 min | **~28 min** | **96% 的浪费集中在下载这一个环节** |

### 下载的 28 分钟是怎么花掉的

| 时刻 | 动作 | 结果 |
|---|---|---|
| 21:12 | `fetch_media --video 1080` 前台跑 | 120 s 被 SIGTERM，文件 0 |
| 21:12 | 同一条命令，超时加到 420 s | 又 SIGTERM |
| 21:14 | **同一条命令改后台** | 21:32 停在 79,691,776（= 19 × 4 MB 整块），21:33 我主动 kill。**累计 21 分钟只拿到 47%** |
| 21:34 | 自写续传：256 KB 子块 + `IncompleteRead.partial` | 从 79.7 推到 93.3 MB，随后某块连续 6 次失败，放弃 |
| 21:37 | 改 **8 线程分段** | 21:40 完成 168,888,822。**71 MB / 3 分钟，是前面 21 分钟速度的 9 倍** |

**根本原因**：旧版 `download()` 用 4 MB 块 + 整块重试。CDN 每次只给 100–600 KB 就断，于是每块都要耗尽重试次数才 raise，然后在 `except` 里删掉文件从头再来——**每重试一次，前面的进度就丢一次**。脚本还带 `time.sleep(1.2*(attempt+1))`，40 块 × 4 次重试 ≈ 纯睡眠十几分钟。

### 五个失误，对应五条已写死的规则

| 失误 | 现在怎么做 |
|---|---|
| **同一脚本失败两次后，第三次只是换后台启动** | **失败两次就换机制**（并发数 / 子块大小 / 下载源），不要第三次重跑同一份代码。已写进 SKILL.md 与 troubleshooting §6.6 |
| 用 `ffprobe` 的 `duration` + `size` 判断"文件完整"，直接去抽帧 → `partial file` / `Invalid NAL unit size` | **判完整性只认 `probe_size` 的 Content-Range 总长**。`duration` 来自 moov，与截断无关；`bit_rate` 是拿 size 反算的，永远自洽 |
| 后台任务写成 `... 2>&1 \| tail -30` | **后台任务不要把 stdout 管道给 `tail`/`head`**——要等 EOF 才输出，整个任务在外层完全静默。让脚本自己控制输出（进度走 stderr 并 flush） |
| 定性卡连改 4 版（7 格 → 删「价值在哪」→ 合并「成熟度」→ 再精简文字），每次重渲染 10 s + 自检 5 s | **定性卡超过 6 格（3 行 × 2 列）必跨页，`vcell-full` 再加一行**。先数格子再写，超了就合并字段。这条现在是可算的，不是猜的 |
| `check_pdf.py` 把 `._pdfcheck/` 写进了 skill 目录 | 自检产物要落在工作目录或 tmp，别污染仓库 |

### 两个做对了的地方（值得保留）

1. **下载没完成就先抽已下载部分的帧。** 79.7 MB ≈ 47% ≈ 400 s，我先抽 45–400 s 的 11 帧，把官方基准表和帕累托图先读到，等下载补齐再抽后半段。**换算方式：可用时长 ≈ 总时长 × 已下字节 / 总字节**，先抽这段的帧，边下边干。
2. **状态栏三件套改变了归因结论。** 画面底下那行「1 轮 · 113 步 · 9.2M tok · 缓存命中 99.6%」，单看任何一个都得不出「920 万是 agent 循环的乘积」——**这类数字必须凑齐「总量 / 步数 / 缓存」三个一起读**。

### 改了什么 / 怎么验证的

| 改动 | 文件 | 验证 |
|---|---|---|
| `download()` 重写为多线程分段 + partial 推进 + 断点续传 | `scripts/fetch_media.py` | 音频 11.2 MB / 3.3 s；续传 61.1 MB / 67 s（0.91 MB/s）；全量 161 MB / 395 s；尾部 830 s 可解码 |
| 新增 `--jobs` / `--chunk` | 同上 | `--jobs 16 --chunk 128` 路径已通 |
| 三条下载硬经验 + 定性卡 6 格上限 + 效率基线补 100–170 MB 档 | `SKILL.md` | 基线表分档后，本次 6.6 分钟落在区间内 |
| 新增 §6.6 故障树 | `references/troubleshooting.md` | 三个症状各自能对上一条病因 |

### 校验型发现（本期内容侧）

- **「agent 任务的 token 要除以步数看」**：9.2M ÷ 113 ≈ 8.1 万/步。视频把它归因为「提示词写了绝对化措辞」，只对一半——措辞抬高的是**步数**，可控旋钮是步数上限。
- **官方两张图的对照组不是同一批**：基准表列 GPT 5.6-Sol，紧接的帕累托图换成 GPT-6.1 Sol / GPT-6 Astra。引用前先核两张图。
- **帕累托图的横轴（每任务费用，对数刻度）被整段忽略**：1017 用 <¥5 拿 77.0%，Opus 5 用 ¥60 拿 74%。分数差 3 点、成本差 12 倍。

## 2026-10-17 · 《「实测」越贵的AI越菜？》—— 18 分钟里 7 分钟是白干的

**视频**：BV11fJX6GEcL，7:41，无官方字幕，A 型（技术·工具横评）
**交付**：HTML + PDF，20 页；评论样本 150/889，7 个观点簇
**触发复盘的原因**：用户反馈"生成用时比较长（18 分钟）"

### 时间去哪了

| 阶段 | 实测 | 其中白费 | 病因 |
|---|---|---|---|
| 取数与媒体获取 | 6.5 min | **~5 min** | yt-dlp 重试 10 次报 567；1080p 单次请求被静默截断（声明 46.3 MB，实收 5.7 MB）；用截断文件抽帧报 `Invalid NAL unit size`；又试了一次 yt-dlp |
| 抽帧与读图 | 3.5 min | ~2.5 min | 定时抽帧 43 张只用 2 张；镜头检测报 82 个"场景"；再逐张读原帧，全轮共读约 18 张图 |
| 写作 | 3 min | 0 | 必要 |
| 渲染与 PDF 自检 | 4 min | **~2 min** | PDF 折叠区整块消失；一次"猜布局"实验改坏又改回 |
| 收尾 | 2 min | 0 | 必要 |

> **真正的成本大头是图片，不是输出 token**：一次整页图读取 ≈ 三四千字文本，本轮图片占输入的约四成。

### 五个失误，对应五条现已写死的规则

| 失误 | 现在怎么做 |
|---|---|
| 连续两次尝试 yt-dlp 下 B站 | **不要用 yt-dlp 下 B站**，必然 567；用 `scripts/fetch_media.py` |
| 1080p 单次请求只拿到 5.7 MB，且截断文件**能被 ffprobe 读出完整时长** | 先 `Range` 探测 `Content-Range` 拿真实总长，再 4 MB 分块，最后校验字节数（已封装） |
| 用 360p 抽帧想读表格 → 只能认出"正确率"三个大字 | **要读数字就直接 1080p**，不做清晰度试探（46 MB / 3 s / 0 token） |
| 定时抽帧 43 张 / 镜头检测 82 个场景 | 用**转写段首**当锚点：同一视频 **17 张**覆盖全部信息页 |
| 为自检读了 8 张整页 PDF 图，实际只有 1 页有问题 | `scripts/check_pdf.py` 先按「内容底线位置」筛，只出可疑页 |

### 两个"校验型发现"从哪来（这条决定了抽帧的价值判断）

| 发现 | 口播说了吗 | 抽帧的目的 |
|---|---|---|
| 榜单写"满分 100"，脚注却是 73.5 + 23.5 = **97** | 完全没提 | 补全 |
| DeepSeek 那题："43 分钟 / 16 元"（口播） vs "115 分钟 / 20.8 元"（贴片烧字） | **说了**，且听着很完整 | **核对** |
| "花费"列混用积分 / 月额度百分比 / 按量 / 点数 | 只说"一个费时一个费钱" | 补全 |

**结论**：只按「字幕有没有信息缺口」判抽帧，会漏掉全部"核对"型发现——而那两个硬伤恰恰出自"口播听起来完整"的地方。

### 顺带修掉的三个 bug

1. `render_report.py`：`@media print{ details > .body{display:block} }` 在 Chromium 上**无效**（闭合 `<details>` 由 UA 的 `::details-content{content-visibility:hidden}` 隐藏），PDF 里折叠内容整块消失。改为打印前 `document.querySelectorAll('details').forEach(d => d.open = true)`。
2. `report.css`：`details[open] summary::after{content:"收起"}` 优先级高于打印块的 `summary::after{content:""}`，PDF 会印出"收起"。已补 `details[open] summary::after{content:""}`。
3. `grab_frames.py`：同目录重跑时旧帧残留，导致"序号 ↔ 时间"**静默错位**。现在抽帧前按前缀清理。

### 这一篇留下的数字（可作下次的基线）

| 指标 | 实测值 |
|---|---|
| 音频下载 | 12.0 MB / 0.6 s |
| 1080p 下载 | 46.3 MB / 3.1 s |
| 转写（large-v3，本地 GPU） | 7.7 分钟音频 / 26.6 s（17.3× 实时） |
| 转写锚点抽帧 | 17 张（同片定时抽帧 43 张、镜头检测 82 个切换） |
| 密集 1 fps + 去重 | 461 → 435 张（去重率仅 5.6%，人像+字幕持续变化） |
| manifest 合并 | 435 帧 → 17 段 |
| PDF 渲染 | 20 页 / 7 秒 / 23 个链接全保留 |
