### 顺带修掉的一类 GBK 崩溃（不止 `check_setup.py`）

**病因**：Windows 下 Python 的 stdout **被管道接走时用系统 ANSI 代码页（cp936/GBK）**，
不是控制台代码页——本机 `chcp` 明明是 65001，`sys.stdout.encoding` 却是 `gbk`。
GBK 编不了 `✅`（U+2705）、`⚠`（U+26A0）、`⇒`（U+21D2）这些字符，
**一旦 print 出去就抛 `UnicodeEncodeError`，进程以 exit 1 结束**——
而此时它报的往往是一条**假失败**（检查全过、补丁已打成功、数据已取到）。

**修法**：全部换成 GBK 能编的等价写法（`✅`→`[OK]`、`⚠️`→`[注意]`、`⇒`→`→`）。

**怎么找出来的**：写了个一次性 AST 审计脚本，扫出**所有运行期字符串常量**里 GBK 编不了的字符
（不止 `print()` 的字面量，还包括"先赋值、后面才打印"的间接路径），
再按 DIRECT-PRINT / indirect 分类。命中 4 处，其中 3 处是**真会炸的**：

| 位置 | 后果 |
|---|---|
| `check_setup.py:141` | 自检全 `[OK]` 却 exit 1 → Agent 误判自检失败，去查一个不存在的故障 |
| `apply-patch.py:145` | **补丁刚打成功**，紧接着的"请重启客户端"提示打不出来，且 exit 1 → 最该看到的一句话没了 |
| `apply-patch.py:102` | 文件状态判为"未知"时（既非 pristine 也非 patched，正是最需要诊断的时刻）直接崩 |
| `fetch_video.py:541` | **主取数脚本**在判读行崩 → 数据其实取到了，但脚本以 exit 1 结束 |

> ⚠️ 这一类 bug 的隐蔽之处：**它只在"输出被管道接走"时发作**——
> 人在终端里直接跑往往完全正常（控制台是 UTF-8），Agent 跑就炸。
> 所以"我本地跑过没问题"不能作为证据，必须**在管道下验证 exit code**。

**验证方式**（复检时用的就是它）：**不设 `PYTHONIOENCODING`** 直接跑脚本，检查 exit code 为 0。

**为什么**

1. **同步方向反了**。Agent 直接接管项目文件夹后，**本地项目目录才是最新的**（含还没提交的改动）。
   从 GitHub 同步会把本地已做但未推送的改动**悄悄回滚掉**——典型的静默错误。
   方向必须反过来：**真源（项目目录）→ 部署副本（各客户端 skills 目录）**。
2. **硬编码的本机绝对路径有三处**（`SKILL.md` / `fetch_comment_media.py` / `troubleshooting.md`），
   指向的是 workbuddy 那个 venv 里的解释器。换个客户端、换台机器就断——
   而 `SKILL.md` 自己在末尾就写着"**不要硬编码任何本机路径**"。自相矛盾。
3. 顺带发现一个**死代码**：`_need_pil()` 从没被调用，"import 失败给友好提示"是假的。

**怎么验证的**

| 用例 | 结果 |
|---|---|
| `sync_skill.py --check`（改造前，MiniMax Code 侧是拷贝） | 正确报出「缺失 1 / 更新 6 / 多余 0」，退出码 1 |
| `sync_skill.py --check`（改造后，两侧都是 junction） | 两侧均显示「[无需同步] 目标就是真源本身（junction）」，退出码 0 |
| MCode skill 加载器穿过 junction | `skill` 工具解析到 `files:///D:/bilibili-video-analysis-summary/SKILL.md`，读到的是**新规则**（第 0 步 / 硬规则 14 / PIL 自动探测均在） |
| `fetch_comment_media.py` 用**无 PIL** 的解释器跑（3.14 venv，无 Pillow） | 自动换到带 PIL 的解释器重跑，输出**不重复**，联系表正常生成（2 张图 → `sheet_01.jpg` 60 KB + `manifest.md`） |
| `fetch_comment_media.py` 用有 PIL 的解释器跑 | 无 INFO 行，直接跑通，行为不变 |
| `check_setup.py` | 5 项全 `[OK]`（补丁 3/3、凭据有效至 2026-11-16、API 200），exit 0 |

### 一个流程性改动：评论默认走 B 通道

原来写「MCP 首选」。但 MCP 拿不到 `pictures` / 等级 / 属地，**也就拿不到 `picture_like_share`**——
用 MCP 取评论，就永远不会知道有 96.8% 的赞藏在图里，**既不会触发读图，也不会发现自己漏了**。
这个漏是静默的，比"少几个字段"严重得多。

改成：**评论一律走 B**（一次调用拿全评论、图片、等级、属地与阈值判读），MCP 只用于字幕关键词定位与章节。

## 2026-10-18 · 重写媒体下载：单连接 64 分钟 → 8 路并发 3–7 分钟

> **⚠️ 本条已部分更正**：「CDN 按连接限速 ~20 KB/s」的归因是错的，实际是本机游戏加速器；标题里的「64 分钟」与正文里的「3–7 分钟」都建立在那个错误前提上。**更正见上一条**（含正确速度与三段式提速数据）。代码修复本身仍然有效，只是参数选得不优。

**类型**：脚本重写（性能/可靠性）+ 文档补规则

**改了什么**

| 文件 | 改动 |
|---|---|
| `scripts/fetch_media.py` | `download()` 重写：4 MB 顺序块 → **多线程分段（`--jobs`，默认 8）+ 256 KB 子块（`--chunk`）+ `IncompleteRead.partial` 逐段推进**；新增断点续传（已存在文件视为可信前缀）与分段校验；新增 `--jobs` / `--chunk` 参数；进度输出到 stderr 并逐行 flush |
| `SKILL.md` | 下载章节补「四道坎」与三段硬经验表；效率基线的「1080p 下载」按文件大小分档；版本实验段补「定性卡 > 6 格必跨页」 |
| `references/troubleshooting.md` | 新增 §6.6「音视频流下不下来：卡死 / 被截断 / 慢得离谱」；快速分诊表加入口 |
| `references/lessons.md` | 追加 2026-10-18 复盘（时间账 + 五个失误 + 两个做对的地方） |

**为什么**

一条 169 MB 的 1080p 视频，用旧版 `download()` 下了 28 分钟只拿到 47%。三个原因叠加：

1. **旧版按 4 MB 块整块重试**，而 CDN 每次只返回 100–600 KB 就断开（`IncompleteRead`）。一块都拿不全 → 耗尽重试 → `except` 里 `os.remove(out_path)` **把已有进度删掉从头再来**。
2. **单连接被限速到 ~20 KB/s**。CDN 按连接限速，4 MB 顺序块等于只开一条车道，169 MB 需要约 1 小时。
3. **`sleep(1.2*(attempt+1))` 的退避**让 40 块 × 4 次重试变成十几分钟纯等待。

后果不只是慢：文件停在 **4 MB 的整数倍**（79,691,776 = 19 × 4 MB），而 `ffprobe` 仍能读出 `duration=849.1`、`bit_rate=750815`（这个值正是拿截断后的 size 反算的，永远自洽），于是一度被当成"完整文件"直接抽帧，直到 `ffmpeg` 报 `partial file` / `Invalid NAL unit size`。

**怎么验证的**

| 用例 | 结果 |
|---|---|
| 音轨（11.2 MB） | 3.3 s，6 段并发，3.4 MB/s |
| 1080p 全量（161.1 MB），首次运行 | 395 s，0.4 MB/s，末字节数与 `probe_size` 一致 |
| 截断到 100 MB 后重跑（续传 61.1 MB） | 67 s，0.91 MB/s，合并后 168,888,822 字节 |
| 完整性 | `ffprobe` duration 849.122063；`ffmpeg -ss 830` 抽帧成功（尾部可解码） |
| 单连接对照（旧版实测） | 0.044 MB/s → 169 MB 约 64 分钟 |

**遗留**

- 4 MB → 256 KB 子块后，小文件（< 8 MB）的请求次数变多，但实测音频仍 3.3 s，无明显回归。
- `--jobs` 上限没有做自适应（例如按失败率自动加线程）。目前靠人工传参，网络极差时建议 `--jobs 16 --chunk 128`。
- 分段校验失败时只报「分段不完整 N/M」并保留 part 文件，**不会自动重试一轮**；需要人工重跑（重跑即续传）。

## 2026-10-17 · 修复 PDF 里折叠区内容整块消失（Chromium 的 ::details-content）

**类型**：修复

**改了什么**

| 文件 | 改动 |
|---|---|
| `scripts/render_report.py` | `to_pdf()` 在 `emulate_media(media="print")` 之后、`pg.pdf()` 之前加一句 `pg.evaluate("() => document.querySelectorAll('details').forEach(d => d.open = true)")` |
| `assets/template/report.css` | 打印块补 `details[open] summary::after{content:""}` |

**为什么**

1. **`@media print{ details > .body{display:block !important} }` 在 Chromium 上不生效**。闭合的 `<details>` 里的内容由 UA 的 `::details-content{content-visibility:hidden}` 隐藏，子元素改 `display` 也进不了盒树——于是 PDF 里整块折叠内容**直接消失**，只在页面上留下一个孤零零的 `<summary>` 行。实测：一份 20 页的报告，末页只剩「4 项 这份报告没有解决的问题」一行，四条正文全部丢失。
2. 连带问题：脚本把 `open` 打开后，屏幕上那条 `details[open] summary::after{content:"收起"}` 的优先级（0,1,2）高于打印块里的 `summary::after{content:""}`（0,0,2），PDF 会在右上角印出「收起」。必须带 `details[open]` 前缀覆盖。

**怎么验证的**

- 修复前：`grep -c "<details>"` 的正文块在 PDF 里只出现 summary 行（该页字数 434 → 补回后 787）
- 修复后：末页四条正文全部可见；`pymupdf` 抽文本校验 `'收起' in page_text == False`
- 同一份报告重渲染：20 页、23 个链接保留、每页字数最少 434（无空白页）

  + `scripts/`（fetch_video.py / check_setup.py）+ `assets/mcp-patch/`
- `scripts/fetch_video.py`：自包含取数（仅标准库），自带 WBI 签名、游标分页、rpid 去重
- `scripts/check_setup.py`：前置条件自检（补丁 / 凭据 / 网络）
- `assets/mcp-patch/`：补丁工具链（整文件替换 + 版本守卫 + 一键还原）

**为什么**
用户希望把"如何做好一份 B站视频总结"固化下来，并要求能分享给别人从零初始化。
关键设计决策：**做成自包含**——即使对方不装 MCP，只用 `fetch_video.py` 也能完成分析。

**怎么验证的**

- `package_skill.py` 校验通过并打包

  "Description cannot contain angle brackets"**；必须写成单行
