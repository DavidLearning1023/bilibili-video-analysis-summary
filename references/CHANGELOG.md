| **新增** `assets/template/report.css` | 长文编辑轨样式表：**全站单一宽度 780px / 正文 19px / 行距 1.78（≈41 字每行）**；单一强调色赭红；禁渐变禁投影；打印 `@page A4 18mm 25mm` |
| **新增** `assets/template/shell.html` | HTML 外壳，占位符 `{{TITLE}}` `{{CSS}}` `{{BODY}}` |
| **新增** `scripts/render_report.py` | 正文片段 + 模板 → 单文件 HTML；`--pdf` 时用 Playwright 渲染 PDF |

**关键设计决策（为什么这么做）**

- **样式表固定、模型只写正文片段** → CSS 不进每次的输出 token（省约 4–5k token/篇），且版式不会因重写 CSS 而漂移。
- **PDF 由同一份 HTML 渲染** → 两者天然一致；折叠区在打印时自动展开，PDF 不丢内容。
- **不引入第二个强调色**：来源区分用墨黑/中灰/描边的**单色梯度**，赭红只留给判定标签与关键数字。
- **正文与图表统一宽度**（首版做成"正文窄 + 图表出血"，用户明确否掉：「图表那个宽度反而合适」）。

**怎么验证的**

1. `python scripts/check_setup.py` → 全绿。
2. 用一期既有分析（`BV1JHYg6yEPY`）的真实内容重制样张：
   - 输出 18 页 PDF，**23 个超链接全部保留**，中文可抽取，渲染 6.5 秒；
   - 实测正文 **41–43 字/行**，与屏幕版一致。
3. 用 Playwright 在 print 媒体下读 `getComputedStyle` 验证列布局（不能只看浏览器视口）。
4. 用 pymupdf 把 PDF 逐页转图**肉眼核查**，抓出「第 7 页几乎全空」「表格没放宽」等问题。

**踩到的三个坑（已写进维护指引）**

1. **窄屏 media query 必须带 `screen` 限定**。打印时 A4 内容宽折算约 605px，不加限定的 `@media (max-width:860px)` 会命中 → PDF 变成移动端单列布局，而屏幕上看不出问题。
2. **高个子图表要加 `class="… tall"`**，否则 `figure{break-inside:avoid}` 会把整页顶空。
3. **`prefer_css_page_size=True` 时边距由 CSS `@page` 决定**，Playwright 的 `margin` 参数会被覆盖——不要再传。

**未做（留给后续）**

- `fetch_video.py` 的 `get_comments()` **仍未抓 `rcount`**（楼中楼回复数）。争议度分析目前要绕开脚本直接调 `/x/v2/reply/wbi/main`。补法是 `walk()` 里加 `"rcount": node.get("rcount") or 0`。
- 观点聚类目前**逐条判读**（每篇 60–100 条）。先试过关键词分类器，46% 落入「未归类」，已弃用。

| `references/troubleshooting.md` | 新增 **§10**：Windows 宿主下 shell 的 `ls`/`head`/`dirname` 全部 `command not found`（Git Bash shim PATH 未装配）——**症状是本命令 stdout 全空、stderr 报 `cd: null directory`**；给出五条绕法（去管道 / 解释器绝对路径 / 改用内置工具 / `-c` 一段式 + `reconfigure(utf-8)` / `run_in_background`） |

**为什么**

本次实战（`BV1bLei6BEGo`，深度访谈样本）暴露了四处缺口：

1. **说话人分离**是最值钱的发现，但 skill 里完全没提。原说明书只教"找错字"，而采访类视频里**归属错了比错一个字严重得多**——观点会被安到错误的人头上。这个缺陷只能靠年龄/生平反推，必须写清楚。
2. **反向核实**是相反方向的陷阱。原说明书通篇在鼓励"主动找误转"，会诱导把受访者的**非标准用词**当成机器错误去"纠正"。本次差点把"大数据学派"（刘慈欣本人原话，学术上应称"连接主义"）错误列入误转清单。
3. **发布时效**：赞／币比判据来自成熟数据，本次遇到的视频**发布仅 4.5 小时**，比值 3.27:1 只能作初判。不加这条警示会误用阈值。
4. **落盘问话**：用户这次在请求里直接说了"总结文档放项目文件夹里就行"，原说明书要求"必须问一次"，会变成明知故问。

**怎么验证的**

- 说话人归属用三条独立线索交叉确认：受访者 1963 年生（当年 34 岁）／采访者 1984 年生（当年 13 岁）／下文出现"但是您看到了" → 判定为采访者自述，与字幕文本的表面读法相反
- 反向核实：检索到受访者在 2025 年另一场公开对谈中使用"大数据领域"指代该技术路线，与其在本视频中的用词一致 → 确认字幕忠实，**不列入误转清单**
- §10 的现象复现前提：连续两次 Bash 调用均 exit 127、stdout 全空、stderr 稳定输出上述两行；改用绝对路径调 `fetch_video.py` 后**一次成功**，产出的 JSON 四个顶层键齐全 → 确认是 shell 环境问题而非脚本问题
- 本次未改动 `scripts/` 与 `assets/`，无需重跑 `check_setup.py`

**遗留**

- 说话人分离目前只有"年龄/生平/称谓反推"这一套人工办法。**是否能用评论区的交叉印证来系统化这一判断，值得后续留意**——本次恰好有两条高赞评论独立描述了受访者的肢体语言，间接支持了口播段落的归属判断
- §10 只在当前这台 Windows 机器上复现过一次，**换机器/换 Agent 客户端版本后可能不复现**；若长期不再出现，应降级或删除该节
- 赞／币比阈值仍为两个样本（沿用下一条的遗留）

| `SKILL.md` · 评论量决策 | 补第二个实测数据点（2,953 条评论取前 20% 时顶层 28.6% 为 0 赞，且尾部出现整段复制最高赞的水帖） |

**为什么**

本次实战（`BV1JHYg6yEPY`，娱乐类样本）暴露了两处说明书缺口：

1. **JSON 结构没写**，导致我连开两次探查脚本才确认键名（`transcript` 里的字幕键实际叫 `lines`），以及**楼层关系无法还原**——试写的父子映射代码白做了一遍。写清楚可以省掉这一整轮。
2. **没有任何"先判断视频值不值得分析"的量化入口**。这条视频 83 秒、AI 换脸、纯虚构，但播放 94 万、评论 2,953 条；而它的赞／币比是 **74:1**（同期技术内容为 1.35:1），这个比值是唯一能在读字幕前就定性"这是情绪型内容"的硬指标。**把它固化下来，可以避免对同类低信息量视频做无谓的精读。**

**怎么验证的**

- 用本次实际 JSON dump 逐键对照新写入的结构表，四项全部吻合
- 赞／币比公式在两组独立数据上复算：`19218/259 = 74.2`、`1335/989 = 1.35`，与文中数值一致
- 评论热度分布重新统计：620 条样本中 ≥100 赞 26 条、50–99 赞 13 条、20–49 赞 36 条、5–19 赞 84 条、1–4 赞 263 条、0 赞 198 条；顶层 395 条中 0 赞 113 条 = 28.6%

## 2026-09-20 · 修复 MCP 三个 bug（评论分页 + limit 上限 + 412）

**类型**：修复

**改了什么**（`@xzxzzx/bilibili-mcp@1.14.1`，5 个文件，合计约 1.8 KB / 78 KB ≈ 2.3%）

| 文件 | 补丁前后 | 改动 |
|---|---|---|
| `bilibili/video-api.js` | 14208 → 14619 B | `getVideoInfo()` 改为 WBI 优先、遇 412 降级到非 WBI |
| `bilibili/comments-api.js` | 4763 → 4927 B | 加 `cursor` 参数，请求带 `next` |

| `utils/validation.js` | 7856 → 7859 B | 上限校验 50 → 300 |

**为什么**（三个独立 bug，都是实测发现）

1. **412 全站失效**：`getVideoInfo()` 调用**不带 WBI 签名**的 `/x/web-interface/view`。
   实测某境外出口 IP：非 WBI = **412**，WBI = **200**（同机同 IP 同时刻）。
   而 `getVideoInfo()` 是 `metadata.js` / `comments-api.js` / `navigation.js` / `subtitle.js`
   的**共同上游**，所以一处失效 → `get_video_metadata`、`get_video_transcript`、
   `get_video_comments`、`get_video_chapters` **全部报 412**。
   已排除：缺 buvid3（补了仍 412）、本机代理（直连一致）、整个 IP 被封（同 IP 其他接口 200）。

2. **评论结果成倍重复**：B站评论接口的 `pn` 页码参数**已被废弃**，传了会被忽略。
   实测 `pn=1/2/3` 返回**完全相同**的 20 条（首条 rpid 均 `318045689904`，加 `sort` 也一样）；
   而 `next=2` 能拿到新数据（首条 `317951091072`）。
   原包按 `pn` 翻页，导致 `limit > 20` 时同一批评论被重复累加
   （`limit=50` 返回 112 条含大量重复，`total_comments` 虚高）。

3. **评论上限过窄**：`limit` 硬编码 1–50，无法满足"按评论总数取前 10%–20%"的需求。

**怎么验证的**
- `node --check` 五个文件全部通过
- 补丁后直接调用 `getVideoInfo("BV1r2ey6EEh5")` → 正确返回标题 / UP主 / 时长 / 分P
- 补丁后 `getVideoCommentsData(limit=50)` → **107 条、0 重复**（修复前：112 条含大量重复）
- `limit=150` → **268 条、0 重复**（含 34 条楼中楼）
- `apply-patch.py` 幂等性测试通过（重复执行跳过）
- 重启客户端后经 MCP 实测：每条评论带 `rpid` 字段、`limit=60` 被 schema 接受 → **三个补丁全部生效**
