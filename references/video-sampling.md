# 视频理解与抽帧密度：市面做法与本项目策略

> 什么时候读：判断「这条视频要不要认真看画面」以及「抽多密」时。
> 所有外部数字标注了来源与核对日期（2026-10-17），厂商文档会变，引用前先复核。

---

## 一、市面怎么做

| 方案 | 采样策略 | 单帧成本 | 关键特点 |
|---|---|---|---|
| **Gemini 静态模式** | **固定 1 fps**，每秒插一个时间戳 | 258 tok（默认）或 66 tok（low）；Gemini 3 用 `media_resolution` 为 70 / 280 | 约 **100 tok/秒**（低分辨率）到 300 tok/秒（高）。官方明确：1 fps 会丢快速动作细节 |
| **Gemini agentic 模式**（3.8 Flash 起） | 模型自己导航视频，按需加载帧／字幕／音频 | 按需 | 长内容最多省 **88% token**、成本降约 66%。本质是**把"抽多密"的决定权交给模型** |
| **Qwen2.5-VL / Qwen3-VL** | **动态 FPS 训练**（慢镜头 1 fps、动作 4+ fps）+ **绝对时间编码**（时间位置 ID 对齐真实时间戳） | 按 patch 数 | 同一模型在不同采样率下都能定位到秒；论文评估上限 **768 帧 / 24,576 video tokens** |
| **Claude** | 原生不收视频文件（只收图片/PDF） | — | 生态工具 `claude-real-video`：场景检测取帧 + 去重 + **按字幕 cue 强制采样** + 单一 `MANIFEST` 时间线。实测 100 秒视频 → 63 个去重帧，20 秒处理完 |
| **ChatGPT** | 不接收视频文件；贴 YouTube 链接只读标题、简介、字幕 | — | 画面完全看不到 |
| **Video-RAG 类** | OCR 层 + ASR 层 + 检测层分别建索引，检索后按时间线合并证据 | — | CARVE（arXiv 2606.13141）把长视频切 2 分钟块、每块生成 4 种表示（视觉/文本 × 帧级/片段级）做 chunk 级选择 → **不存在万能的单一配置** |

### 三条可迁移的结论

1. **固定 1 fps 只是默认值，不是最优值。** 1 小时视频按 1 fps 是 3,600 帧 ≈ 93 万 token——所以 Google 才在 2026 年加了 agentic 模式。**"抽得越密越好"在长内容上是错的。**
2. **顺序靠时间戳／manifest 承载，不靠模型自己记。** Qwen 把时间写进位置编码，Claude 生态把帧和字幕合进一份清单——两条完全不同的路，解决的是同一个问题：先后逻辑。
3. **有效帧数有天花板。** 主流实现落在 **300–800 帧**（Qwen 评测上限 768，CARVE 两小时约 300）。超过之后是上下文稀释，不是理解增强。

## 二、频率怎么定：按事件，不按秒

均匀采样的问题不在"漏"，在**它把预算平均花在了没变化的地方**。正确做法是先算预算，再按事件分配。

```
N   = 视觉 token 预算 ÷ 单帧成本        # 总帧数上限
E   = 事件数 ≈ 去重后的场景切换数（或字幕段数）
fps ≤ N / T                            # 预算约束
fps ≥ k × E / T                        # 事件约束，k = 2~3（一个事件至少前、中、后三帧）
```

两条兜底：
- **保底层**：即使检测不到事件，也保证 `1/10 fps`（10 分钟 60 帧），防止漏掉缓慢变化。
- **上限**：`min(N, 600)` 帧。超过 600 帧，优先提高"每一帧的信息密度"（分辨率、裁剪），而不是加帧。

### 按内容类型给的经验值

| 内容类型 | 事件率 | 建议密度 | 说明 |
|---|---|---|---|
| 幻灯片／横评／财报 | 3–5 次/分钟 | **0.2–0.3 fps** + 事件补帧 | 一页 PPT 停留十几秒，密采样纯浪费 |
| 软件演示／写代码 | 8–15 次/分钟 | **1 fps** 起，配 `--dedupe` | 一个点击可能只占 0.3 秒，低于 1 fps 会漏 |
| 快速动作／剪辑密集 | 30+ 次/分钟 | 2–4 fps | 只有这类才需要高帧率 |
| 纯口播／访谈／段子 | <1 次/分钟 | **0 帧** | 画面不承载信息 |

## 三、本项目怎么做（成本单位是"读图次数"，不是 token）

一次整页图读取 ≈ 3,000+ token，比抽一万帧还贵。所以**密集抽帧必须先在本地压成结构，再喂给人读**：

```bash
# 1) 全量抽帧 + 去重（本地跑，0 token）
python scripts/grab_frames.py video1080.m4s --dense 1 --dedupe --out frames --srt audio.srt

# 2) 得到 manifest.md：帧按口播切成 17 段，每段给「时间范围 + 帧区间 + 张数」
#    顺序与上下文由文件承载，读图的人不需要自己记

# 3) 只读每段首帧 + 变化点，通常 15–25 张
# 4) 超过 30 张就分段读，不要一次全塞
```

**判据（我们自己用）**：

| 情况 | 做法 |
|---|---|
| `--dense 1 --dedupe` 后帧数 **> 600** | 说明内容不需要这么密，降到 0.3 fps 或改用转写锚点 |
| 去重率 **< 20%**（435/461 这种） | 画面一直在动（人像/录屏），去重救不了，改按事件抽 |
| 去重率 **> 70%** | 典型幻灯片，`--dedupe` 效果最好，可以放心用 1 fps |
| manifest 里某段 **帧数 > 60** | 这一段大概率是"讲很久但画面没变"，可以只留首尾两帧 |

## 四、判定为「画面为主」之后：问用户，但给三个选项

不要给二选一。「只看评论区」和「认真看片」之间，有一个成本接近前者、信息接近后者的选项。

| 选项 | 成本（以 8 分钟视频计） | 产出 | 什么时候选 |
|---|---|---|---|
| **A. 只看评论区 + 外部检索** | 最低（1–2 分钟） | 关于视频的**讨论**，不是视频内容本身。评论说的是"我觉得"，不是"视频讲了什么" | 只要舆论反应 / 视频本身没有可信数据 |
| **B. 结构化看片** | 中（4–6 分钟，读 15–25 张图） | 分段时间线 + 画面原件（表格、参数、界面） | 需要视频的**内容**，尤其需要数字 |
| **C. 混合：评论定位 + 定点精读**（推荐） | 中偏低（2–4 分钟） | 观众认为重要的那几段 + 它们的画面证据 | 大多数情况。评论区就是免费的"注意力热力图" |

**为什么 C 常常最优**：评论天然筛掉了没人关心的段落。一份 8 分钟的视频，观众反复争论的通常只有 2–3 段——只精读这 2–3 段，成本是 B 的三分之一，信息密度反而更高。
